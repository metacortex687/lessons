В целом решение с эталонным совпадает. 

Решил отказаться от `size()`, а использовать метод `count()`, чтобы подчеркнуть его отличие от `capacity()`, который по факту используется.

Вместо `get()` использую `find()`, на мой взгляд, `get()` лучше, нравится идея бедной семантики, когда используется поменьше новых слов, если можно обойтись существующими.

По реализации:

Для того чтобы вычислить стартовую позицию в массиве, откуда искать ячейку для значения, мне нужно строковое представление объекта. В случае строки это сама строка и есть. В случае произвольного объекта он должен быть производным от:

```TS
abstract class Hashable {
    abstract hash(): string;
    abstract equals(other: Hashable): boolean;
}
```

Метод `hash` отдает уникальную строку, идентифицирующую объект, необходимо для вычисления стартового индекса, куда помещать объект. 
Метод `equals` необходим — для сравнения объектов. 
В случае неправильной работы `hash()`, например, когда для разных объектов будет одна хэш-строка, хэш-таблица будет работать неэффективно. В случае неправильной работы `equals()` будет работать неправильно.

Для реализации HashTable сделал дополнительный тип данных `StringHashTable`. В `StringHashTable` в явном виде надо передавать хэш. Например, для метода `put()`: `put(value: T)` в `HashTable`, а в  `StringHashTable` `put(key: string, value: T)`.

Нашел ошибку в реализации: наличие свободного слота в массиве для помещаемого элемента определяю по значению там undefined, но на это же значение и очищаю при удалении. А при поиске значения, чтобы определить, есть оно там или нет, останавливаюсь, когда значение найдено, или если в ячейке значение undefined — это значит, дальше искать нет смысла и значения нет в таблице. Учел проблему уже при реализации ассоциативного массива, использую еще один тип пустого значения null.
