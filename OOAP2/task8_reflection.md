#### Объектные типы, параметризация типами, ковариантность и контравариантность, наследование

Есть отношение родитель-потом, и есть отношение тип-подтип. Отношение родитель потомок возникает в ООП в результате наследования классов. При это потомок является подтипом родителя. Работает динамический полиморфизм, мы можем переменной задекларированной с типом родителя, присвоить значение с типом потомка. Это возможно поскольку потомок реализует интерфейс родители. Обратное невозможно, так как родитель не знает что нового в интерфейсах потомков.

За основу для определения тип-подтип, возьму возможность для переменной с задекларированным типом типа присваивать значение с типом подтипа.

Запишу это используя краткую нотацию:
a:: A - переменная `a` имеет тип `A`
b:: B

B <: A - B является подтипом переменной A

$\frac{B <: A, a:: A, b:: B}{a := b}$ смысл выражения -  переменной `a` можно присвоить значение переменной b и присваивание корректно по типам.


Следующий способ появления типов это параметризация одного типа другим. При этом появляются понятия ковариантности и контравариантности.

Запишу таблицей.

|                   | Тип параметр <br> | Тип параметр <br> | Производный тип | Производный тип |
| ----------------- | ----------------- | ----------------- | --------------- | --------------- |
|                   | T1                | T2                | `A<T1>`         | `A<T2>`         |
| Ковариантность    | Тип               | Подтип            | Тип             | Подтип          |
| Контрвариантность | Тип               | Подтип            | Подтип          | Тип             |
|                   |                   |                   |                 |                 |


Если совместить появления типов в результате наследования и в результате параметризации. То-есть параметризуем A и B, типами T1 и T2, получается `A<T1>` и `B<T2>`. При этом про отношение между A и B, можно сказать, что это родитель - потомок , так как B реализует все методы  A. Но говорить, что  отношение тип-подтип, не можем так как нет переменных типа A или B, пока их не параметризовали (хотя возможно в каком-то контексте A и B это так-же типы).

И тут возникаем противоречие. Если B потомок A. A T2 подтип `T1`. То какое будет отношение тип-подтип для `B<T2>` и `A<T1>` в случае контравариантной параметризации типом. С одной стороны поскольку B потомок A, следует что `B<T2> <: A<T1>`. С другой стороны поскольку типизация контравариантная и `T2 <: T1` следует, что `A<T1> <: B<T2>`. Возникает противоречие из чего делаю вывод, что такие случаи невозможны.

В случае ковариантной типизации и совпадением с направлением наследования или инвариантной типизации противоречий нет.

Формально возможен еще один вариант контрвариантная типизации и наследования, когда он не противоречит направлению наследованию.

#### Ковариантность функциональных типов

Думаю отказаться от понятия декларация типа. Достаточно использовать понятие допустимости присваивания значения переменной одного типа переменной другого типа.

Таким образом `B <: A` (B является подтипом типа A) если для переменных  `a::A` (переменная `a` типа `A`) и `b::B`  допустимо `a := b` (допустимо присваивание значения). Подходит для объектных случаев когда типы появляются в результате наследования.

В случае для функциональных типов контравариантность заложена изначально и является следствием использования ими объектных типов - "параметризации объектными типами".

Типы функций буду описывать так:

$FA \overset{\mathrm{def}}{=} (A->C)$  
$FB \overset{\mathrm{def}}{=} (B->C)$  

где A, B, C - объектные типы. А `(A -> C)` обозначает, что это функция которая принимается аргумент типа A, и возвращается значение типа C. 

Есть переменные:
`fa::FA`, `fb::FB`, `a::A`, `b::B`

Вызов функции буду записывать например так:
`fa(a::A)::C` сразу указывая для удобства типы.

Ковариантность функционального типа при параметризации объектным типом можно записать так:

`B <: A => FA <: FB`
или `B <: A => (A -> C) <: (B -> C)`

Согласуется с определением ранее, того что значит является подтипом: это значит можем переменной с типом типа присвоить значение переменной с типом подтипа и использовать далее ничего не зная об этом.

То-есть я могу вместо функции
`(B -> C)` использовать функцию `(A -> C)` если `B :< A`, так как могу использовать в качестве переменной типа `A` всегда переменную типа `B` поскольку это позволяет динамический полиморфизм. Это будет корректно по типам.

##### Контравариантные примеры

Рассмотрю в первую очередь контравариантные примеры, так как это вызывало наибольшую сложность.

**Пример 1 из эталонного решения:**

Буду использовать нотацию используемую ранее.

Даны объектные типы `Person`, `Sportsman`, `Policeman` и отношение между ними определённое через наследование
`Sportsman <: Person` (непривычно направление стрелочек, то что отлично от UML)
`Policeman <: Person`

Даны функциональные типы. Определение функции в коде python считаю определением функционального типа и переменной одновременно.

`person_run :: Person -> None`
`sportsman_run :: Sportsman -> None`
`policeman_run :: Policeman -> None`

И дана функция:
`make_sportsman_run :: Sportsman -> (Sportsman -> None) -> None`
которая на вход промает объект типа `Sportsman` и функцию `(Sportsman -> None)`, поскольку функции контравариантны, то вместо `(Sportsman -> None)` можно использовать `(Person -> None)` и это будет корректно по типам.

Что и происходит в коде в котором можно вызвать как
`make_sportsman_run(Sportsman(), sportsman_run)`
так и
`make_sportsman_run(Sportsman(), person_run)`, поскольку person_run может принимать в качестве аргумента и потомков типа который в аргументе.


**Пример 2 из эталонного решения:**

Объявлен Generic "обертка" для контравариантной параметризации
```python
T_contra = TypeVar('T_contra', contravariant=True)

class _T(Generic[T_contra]):
    def __init__(self, item: T_contra) -> None: ...
```


Объявлена иерархия классов:
```python
class BladedWeapon: pass
class Sword(BladedWeapon): pass
class Broadsword(Sword): pass
class Cutlass(Broadsword): pass
class Shuriken(BladedWeapon): pass
```

Объявлена функция которая принимает тип c контрвариантный параметризацией:
```python
def sharpen_melee_weapon(weapon: _T[Broadsword]) -> None: pass
```

И соответственно можем использовать:

```python
sword1, sword2 = _T(Broadsword()), _T(Sword())
sharpen_melee_weapon(sword1)  # OK
sharpen_melee_weapon(sword2)  # OK
```


**В качестве третьего примера контрвариантности выберу свое решение:** 

У меня есть два типа Document и PdfDocument.
PdfDocument <: Document

Задекларировал тип для контрвариантной типизации
```python
DocumentT = TypeVar(
    "DocumentT",
    bound=Document,
    contravariant=True, #декларируем допустимость контрвариантности
)
```

Класс принтер с ковариантной параметризацией типом.

```python
class Printer(Generic[DocumentT]): #ковариантная параметризация типом
    def print(self, document: DocumentT) -> None:
        print(f"Печатаю: {document}")	
```


Далее поскольку `Printer[Document] :< Printer[PdfDocument]` и поскольку типизация контравариантная, то возможно присваивание вида `a::Printer[PdfDocument] := b::Printer[Document] `

А в коде python это:
```python
pdf_printer: Printer[PdfDocument] = Printer[Document]()
```

и далее уже вызов соответствующего метода
```python
pdf_printer.print(PdfDocument("Новый документ", ""))
```
